# 症状イラスト選択型ナビ MVP 設計メモ

## 結論

最初のMVPは「病名検索」ではなく「症状イラストを選んで、受診判断と鑑別候補の整理に進むナビ」として作る。

診断アプリに見せすぎると医療リスクと規制リスクが跳ねるため、ユーザー向けの主語は「症例を絞る」ではなく「症状の整理」「緊急度の確認」「医師に伝える材料づくり」に寄せる。

## 体験コンセプト

ユーザーは文章入力から始めない。最初に体の部位・症状イラストを選ぶ。

1. 体または症状カテゴリのイラストを選ぶ
2. 追加の症状カードを選ぶ
3. 期間・強さ・急性度・危険サインを短く確認する
4. 緊急なら即時受診導線を出す
5. 緊急でなければ、考えられる症状パターン、除外できない候補、医師に伝えるメモを出す

## 最初に扱う範囲

MVPの対象は「発熱・咳・息苦しさ」に限定する。

理由:

- 危険サインが比較的定義しやすい
- ユーザーが入力しやすい
- 普通検索とRAGの両方を試しやすい
- いきなり全身症状を扱うより検証がしやすい

## 症状カード例

| card_id | 表示ラベル | イラスト方向 | 内部状態 |
|---|---|---|---|
| fever | 熱っぽい | 体温計・赤い額 | yes/no/unknown |
| cough | 咳が出る | 口元・咳の動き | yes/no/unknown |
| dyspnea | 息苦しい | 胸を押さえる・呼吸 | none/mild/moderate/severe |
| chest_pain | 胸が痛い | 胸部に痛みマーク | yes/no/unknown/red_flag |
| sudden_onset | 急に始まった | 時計・稲妻 | yes/no/unknown |
| confusion | ぼんやりする | 頭部・混乱マーク | yes/no/unknown/red_flag |
| blood | 血が混じる | 赤いしずく | yes/no/unknown/red_flag |
| child_or_pregnant | 小児・妊娠など | 家族・妊婦アイコン | yes/no/unknown |

## 内部データモデル

表UIは2択中心に見せるが、内部では3択/4択で保持する。

```json
{
  "session_id": "local-or-anonymous-id",
  "selected_cards": [
    {
      "card_id": "dyspnea",
      "value": "moderate",
      "confidence": "user_selected",
      "asked_at_step": 2
    }
  ],
  "red_flags": ["severe_shortness_of_breath"],
  "search_terms": ["発熱", "咳", "息苦しさ"],
  "rag_context_ids": ["source.medlineplus.emergency-signs"],
  "output_mode": "triage_and_summary"
}
```

## 判定レイヤー

1. Safety Rules
   - 緊急サイン、年齢、妊娠、既往歴、急性発症など
   - ここはLLM任せにしない

2. Structured Search
   - 症状語、同義語、部位、期間、重症度で候補を引く
   - 完全一致と表記ゆれに強くする

3. RAG
   - 根拠説明、受診目安、医師に伝えるメモの生成に使う
   - 診断断定には使わない

4. LLM
   - ユーザー向けの説明整形
   - 不明点の次質問生成
   - 根拠のない断定は禁止

## 出力方針

出力は病名ランキングではなく、次の形にする。

```text
いま優先して確認すること:
- 息苦しさが強い、胸痛、意識がぼんやりする、血が混じる場合は急いで医療相談。

整理された症状:
- 発熱あり
- 咳あり
- 息苦しさは中等度

除外できないパターン:
- 呼吸器感染症
- 喘息・気道過敏
- 肺炎など医療機関で確認が必要な状態

医師に伝えるメモ:
- いつから
- 体温
- 息苦しさの程度
- 胸痛や血痰の有無
- 持病と服薬
```

## UI構成

最初の画面:

- 上部: 「気になる症状を選んでください」
- 中央: 症状イラストカードのグリッド
- 下部: 選択済みカードの横並びチップ
- 常時表示: 「緊急症状がある」ボタン

カード選択後:

- 追加確認カードを2から4枚だけ出す
- すべて質問にしない
- 重要度の高い確認から出す
- 「わからない」を必ず用意する

結果画面:

- 緊急度
- 症状サマリー
- 除外できない候補
- 受診・相談の目安
- 医師に見せるメモ
- 参照した根拠

## Fatal Risk

一番危ないのは「イラストで簡単に病名がわかる」印象になること。

影響:

- ユーザーが受診を遅らせる
- 誤った安心を与える
- 医療機器・臨床判断支援として扱われる可能性が上がる

潰し方:

- 病名断定UIを避ける
- 緊急サインは最優先で分岐
- 出力名を「候補」より「受診時に確認されやすい観点」に寄せる
- 根拠、更新日、回答不能を必ず表示する

今やるべきか:

- 今すぐやるべき。後から付けるとUIとデータ構造を作り直すことになる。

## 代替案

症状イラスト選択ではなく、体の部位マップから入る案もある。

強み:

- 腹痛、頭痛、胸痛など部位主導の症状に強い
- ユーザーが「どこが変か」を言いやすい

弱み:

- 発熱、だるさ、咳、不安感など全身・機能症状に弱い
- 初回MVPでは実装範囲が増えやすい

判断:

- 最初は症状イラストカード方式がよい。
- 2段目に部位マップを追加できる構造にしておく。

## 次の30分タスク

「発熱・咳・息苦しさ」だけで、12枚の症状カードと10個の安全ルールを定義する。

完了条件:

- 症状カード一覧がある
- 各カードに内部値がある
- red flag になる条件がある
- 結果画面の文言テンプレートがある
- RAGが参照すべき根拠タイプが分かれている
